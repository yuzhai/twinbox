# 问题定义

本文只回答三个问题：**问题是什么、它出现在哪些场景、怎样才算解决。**
方案与架构不在这里，见 `docs/architecture.md`（草案）。

## 一句话

我们已经有能力让 agent 替我们操作真实系统，但**没有一种方式能让它拿不到我们的秘密**：
要么把完整的机器和凭据都交给它，要么把它关进一个干不了活的笼子。

## 1. 现状

编程 agent（Claude Code、Codex、opencode2、dsh 等）已经进入日常工作流。它们不是聊天窗口，
而是**会执行命令的进程**：读代码、改文件、跑测试、装依赖、调 API、开 PR、连数据库、
操作生产环境。

为了让它干活，我们实际上做了两件事：

1. 把它放在自己的机器上，能读 `~/.ssh`、`~/.aws`、浏览器 cookie、shell 历史；
2. 把自己所有的 token、密码、密钥以环境变量或配置文件的形式交给它。

其中 **SSH 私钥是最严重的一项**：它不是"某个服务的凭据"，而是"你是谁"。

结果是：**一个由模型输出驱动的进程，拥有了开发者的全部权限。**

## 2. 问题的四个组成部分

| 编号 | 问题 | 具体表现 |
| --- | --- | --- |
| **P1** | 凭据扩散 | key 出现在环境变量、`~/.ssh`、`~/.git-credentials`、`~/.npmrc`、MCP 配置的 `environment`、agent 的 history 与日志里；一旦进入 agent 上下文，就再也收不回来 |
| **P2** | 环境与权限不可分 | agent 要干活就必须看到真实的项目、真实的依赖、真实的网络；而这些恰好和宿主机权限绑在一起 |
| **P3** | 传统沙箱的反作用 | 为了安全把环境削到只剩骨架，agent 装不了包、连不上网、跑不了测试，用户最终关掉沙箱，问题回到原点 |
| **P4** | 授权粒度缺失 | 即使藏住 key，agent 仍可以"借用"它去调用（confused deputy）；用户既无法限制它能做什么，也无法事后核对它做了什么 |

P1 是大家最常讨论的，P4 是最容易被忽略的，而 P3 决定了方案能不能被真正使用。

### 2.1 SSH 密钥是更麻烦的一类

把 SSH 私钥和 API key 放在一个表里讨论会低估难度：

| 维度 | API key / token | SSH 私钥 |
| --- | --- | --- |
| 作用域 | 可按服务、按接口缩小 | 代表"你是谁"，对所有信任它的主机生效 |
| 过期 | 通常有 TTL，可轮换 | 多数无口令、无过期概念 |
| 撤销 | 平台侧一键失效 | 要逐台机器改 `authorized_keys` |
| 审计 | 网关能记录每次调用 | 服务端只记录"登录过"，不记录做了什么 |
| 使用面 | 一个 API | git、部署、`scp`/`rsync`、ansible、跳板、隧道都用它 |
| 泄露后果 | 单个服务 | **横向移动到所有信任它的机器** |

还有两个只在 SSH 上出现的机制，直接决定了方案形态：

1. **agent forwarding**：`SSH_AUTH_SOCK` 让进程**不读私钥也能完成签名**。这是"可用但不可读"的原生形态，也是最大的风险点——一旦把 socket 带进沙箱，沙箱内任何进程都能借用你的身份登录所有机器。反过来说，它也是解法：SSH 的正确做法不是"藏文件"，而是"把签名变成一次受策略约束的委托"。
2. **隧道**：`ssh -L / -R / -D` 是通用隧道。**一条被允许的 SSH 连接等于一个通用出站通道**，能绕过任何基于域名或端口的白名单。想靠"网络白名单"做隔离，就必须同时处理隧道。

因此 SSH 不能简单归入"凭据"一类，它同时是**身份、文件、通道**三件事。

## 3. 为什么现有做法不够

| 做法 | 解决了什么 | 没解决什么 |
| --- | --- | --- |
| Docker / 容器沙箱 | 进程隔离 | 权限过大（常挂宿主目录、docker.sock）、无凭据方案、配置复杂 |
| microVM（Firecracker 等） | 隔离强度 | 重、慢、桌面部署困难，对"凭据"零帮助 |
| 各家的 agent sandbox（bwrap / Seatbelt 封装） | "跑在哪" | "能拿什么"与"能做什么"；对 MCP 与多 agent 无方案 |
| 密钥管理器（Vault、1Password CLI） | 集中存储 | 取用时明文仍进入 agent 进程内存与上下文 |
| AI gateway | LLM 调用的密钥与配额 | MCP 工具、宿主文件、系统操作完全不覆盖 |
| MCP 网关 | 工具侧的凭据 | 宿主环境、文件、LLM 调用不覆盖 |

结论：**没有一个现成件同时覆盖"环境、凭据、工具、授权"四件事**，而用户需要的是装一次就生效。

## 4. 使用场景

下面这些场景来自真实工作流，不是设想。判断方案是否成立，看它能不能同时覆盖它们。

### S1 日常编码与依赖安装

改代码、跑测试、装依赖。需要出站到 npm / PyPI / Go proxy。
**今天的失败模式**：为了让 agent 能装包，必须把网络完全打开；网络一开，凭据也能被外发。

### S2 代码托管操作

读 issue、看 CI、开 PR、推到 feature 分支。需要 GitHub token。
**今天的失败模式**：token 常年在 `~/.git-credentials` 或 `gh` 的配置里，agent 能读也能推，
且可以推到任何仓库、任何分支。

### S3 线上排障

读日志、查指标、跑只读 SQL。需要内网凭据或 VPN 身份。
**今天的失败模式**：要么把生产 kubeconfig / 数据库密码放进 agent 环境，要么在自己的机器上
直接跑 agent —— 两种都是把生产交出去。

### S4 生产变更

部署、扩缩容、回滚、改配置。属于高危操作。
**今天的失败模式**：没有审批环节，agent 一次"顺手"的调用就能改动生产。

### S5 第三方 SaaS（MCP）

Slack、Notion、Jira、Linear 等，每个服务一个 token。
**今天的失败模式**：token 被明文写进 MCP 配置的 `environment` 字段，而这些配置就在
agent 会读的目录里。这是本议题明确指出的问题。

### S6 多 agent 并存

同一台机器上同时使用 Claude Code、Codex、opencode2，各自有配置、历史、缓存。
**今天的失败模式**：给 agent 一个 home 目录，就把这些历史连同里面的凭据一起给了它；
不给，agent 就失去了项目上下文。

### S7 不可信输入

仓库文件、issue 正文、网页、工具返回都可能包含针对 agent 的指令。
**今天的失败模式**：prompt injection 成功后，agent 用它的**合法权限**做坏事 ——
藏住 key 并不能阻止它把数据发走，也不能阻止它删仓库。

### S8 交接与复现

把环境交给同事、录 demo、写教程。
**今天的失败模式**：必须带上自己的账号与 key，录屏里一不小心就是真实凭据。

### S9 泄露响应

怀疑某个 key 被用过了，需要立刻止血并搞清发生了什么。
**今天的失败模式**：要逐个服务手工轮换，且没有任何记录能回答"agent 到底调用过什么"。

### S10 SSH：远程主机、部署与跳板

通过 SSH 登录服务器、传文件、跑部署脚本、用 `ssh -L` 连内网数据库，或让 git 走 `git@` 协议。
**今天的失败模式**：

- 私钥（多数没有口令）就在 `~/.ssh`，agent 既能读也能拿去登录**所有**信任它的机器；
- `SSH_AUTH_SOCK` 一旦被转发进沙箱，agent 不用读私钥就能签名，且无法区分是你在操作还是它在操作；
- 允许 SSH 出站等于开了一条通用隧道，`-L/-D` 可以直接绕过任何域名白名单；
- `~/.ssh/config` 与 `known_hosts` 本身泄漏内网拓扑（跳板机、主机名、端口），属于敏感信息但不是"密钥"，最容易被忽略；
- 出事以后要逐台机器改 `authorized_keys`，且无法回答"这把 key 被用来登录过哪些机器"。

## 5. 目标与非目标

**目标**

1. 沙箱内的 agent 拿不到任何凭据、读不到任何敏感文件，且这一点可被验证而不是被声明。
2. 沙箱内的环境足够完整：主流 agent 不改代码、不装插件即可正常干活。
3. 配置成本接近零：不写策略文件、不重新录入机器上已有的 key。
4. 高危动作有闸门，出事可追溯、可撤销。
5. SSH 身份不以文件形式进入沙箱：需要时以受控签名或受策略约束的跳板代替，隧道默认关闭。

**非目标**

- 不追求虚拟机级隔离，也不承诺防御内核提权
- 不替代密钥管理系统，不做企业级多租户
- 不解决模型供应商被攻陷的问题

## 6. 成功判据

一个方案算成立，需要同时满足：

| # | 判据 | 验证方式 |
| --- | --- | --- |
| 1 | 沙箱内不存在任何凭据 | 对完整快照做密钥扫描，零命中 |
| 2 | 敏感文件零挂载 | 黑名单路径逐条断言不存在 |
| 3 | 出站默认拒绝 | 未授权域名与元数据地址均不可达 |
| 4 | 撤销立即生效 | 宿主删除凭据后下一次调用失败 |
| 5 | 零配置可跑通 | 不写任何规则文件，完成一次对话与一次 MCP 调用 |
| 6 | 注入不能扩大权限 | 诱导外发/删仓库的尝试被拒且留痕 |
| 7 | SSH 只能以受控身份使用 | 沙箱内无私钥文件、无可用 agent socket、隧道默认禁止 |

判据 6 是分水岭：前五条只证明"藏得好"，第六条才证明"拿不到也用不了"。
判据 7 是 SSH 的对应条款——它检验方案是否理解"身份、文件、通道"是三个不同的问题。
