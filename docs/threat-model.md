# 威胁模型

状态：基线 v0（2026-10-24）。威胁假设与不做清单是实现的判据，改动需走 PR。

## 1. 边界定义：什么算敏感

这个系统里"敏感"不是由内容判断的，而是由**位置与通道**判断的：

1. **位置**：沙箱之外的一切属于敏感域——宿主凭据、私钥、宿主 home、生产配置。
2. **通道**：进入沙箱的只有两种东西——用户主动放入的文件、运行时产生的数据流。
   前者受"入箱审查"约束，后者不受（见 T14）。
3. **声明**：经审查通过并记录在案的文件，视为"用户已声明可接受"，不再作为敏感资产跟踪。

由此得到一条工作定义：

> **沙箱内 = 用户声明可以公开的内容。**
> 敏感信息 = 尚未进入沙箱的一切 + 运行时流入且未被声明过的数据。

这不等于"箱内绝对安全"。它只是把"是否敏感"的判断权交给用户，并要求这个判断**可追溯**：
谁在什么时候把什么放了进去、审查结果是什么、有没有跳过。判断错了可以回查，这才是可控的。

## 2. 信任边界

```
可信      │  宿主：twinbox CLI、密钥库、broker、MCP gateway、用户
──────────┼─────────────────────────────────────────────────────
审查点    │  入箱审查：路径黑名单 + 内容扫描 + 默认阻断 + 记录
──────────┼─────────────────────────────────────────────────────
不可信    │  沙箱内一切：agent、模型输出、放入的项目文件、MCP 响应、依赖包
──────────┼─────────────────────────────────────────────────────
半可信    │  经 broker 访问的外部服务
```

宿主"可信"只体现在它持有密钥这一点上。**任何处理 agent 可控输入的进程**
（包括 broker 和每个 MCP server）都按潜在 confused deputy 对待：
必须与它不需要的秘密隔离。

## 3. 假设

- **A1** agent 已被完全攻陷：假设任意时刻都可执行任意代码，而不是"提示变坏之后"。
- **A2** 提示注入必然发生：agent 读到的文件、issue、网页、工具返回都可能带指令。
- **A3** 用户不会读文档，遇到弹窗倾向于直接确认。**因此高危项必须默认阻断，
  不能把判断权交给一次点击。**
- **A4** 内核未被攻陷（不防御 0day 提权）。
- **A5** 模型供应商只返回模型输出，不主动作恶。
- **A6** 用户对"什么可以放进沙箱"的判断是最终依据，但每次判断都要留下记录。

## 4. 资产（全部位于沙箱之外）

| ID | 资产 | 丢失后果 |
| --- | --- | --- |
| A1 | LLM 供应商密钥 | 资金损失、账号被接管 |
| A2 | Git / CI token | 供应链投毒 |
| A3 | 云凭据 | 基础设施被接管 |
| A4 | 宿主 SSH 私钥、`ssh-agent` socket、keychain、浏览器 cookie | 身份被接管、横向移动 |
| A5 | 生产系统 | 故障与数据损失 |
| A6 | 入箱之前的仓库内容与 `.git` 历史 | 历史提交里残留的密钥外泄 |
| A7 | 运行时流入但未经审查的数据（API 返回、工具结果、日志、查询结果） | 违反合规、客户数据外泄 |

A6 与 A7 是两类特殊资产：它们不在"文件"这条通道上，因此不受入箱审查保护。

## 5. 威胁与缓解

| ID | 威胁 | 缓解 | 残留风险 |
| --- | --- | --- | --- |
| T1 | agent 从环境变量/参数读到凭据 | 只注入占位符，真值不出宿主 | 低 |
| T2 | agent 扫描文件系统找密钥 | 宿主 home 永不挂载；箱内只存在已审查内容 | 低 |
| T3 | agent 读 `/proc/*/environ`、core dump、自身日志 | 箱内本来就不存在真值 | 低 |
| T4 | agent 向任意地址外发数据 | `--unshare-net`，仅 loopback，白名单 broker | 低（防的是数据流向，不是内容） |
| T5 | agent 把 broker 当"万能代理"使用 | 按目标 + 方法级白名单、限速、审计 | **中** |
| T6 | agent 滥用合法 MCP 工具（删仓库、改权限） | 参数级策略 + 破坏性动词审批 | **中** |
| T7 | agent 把数据写回项目目录并试图带出 | 出箱时快照扫描 + diff 复核 | 中 |
| T8 | MCP server 本身恶意 | 每个 server 独立身份、无宿主 home、默认无网络 | 中 |
| T9 | 密钥泄漏进 TwinBox 自己的 git 历史 | `.gitignore` 黑名单 + pre-commit 扫描 | 低 |
| T10 | 箱内获得 `ssh-agent` socket，免读私钥即可签名 | socket 永不挂载；需要时改走宿主侧受策略约束的签名代理 | **中高** |
| T11 | 通过 `ssh -L/-R/-D` 建立通用隧道，绕过出站白名单 | SSH 出站默认禁止；放行时只允许到指定主机端口，禁隧道与转发 | **中高** |
| T12 | `~/.ssh/config`、`known_hosts` 泄漏内网拓扑 | 不入箱；按需生成最小条目 | 中 |
| T13 | 用户误把敏感文件放入沙箱（漏审或跳过审查） | 入箱审查：路径黑名单 + 内容扫描 + 高危项默认阻断 + 记录；跳过必须显式 override 并留痕 | 中 |
| T14 | 运行时数据未经审查进入上下文（API 返回、工具结果） | 出站白名单限制来源；按来源分级 | **中高** |

**T5、T6、T10、T11、T13、T14 是本方案诚实的弱点**：它们靠策略与审计缓解，不靠隔离。
任何对外表述都不应越过这一层。

T13 与 T14 是一对：审查管得住"用户放进去的文件"，管不住"系统帮他取回来的数据"。
把这两件事混为一谈，是这类方案最常见的过度承诺。

## 6. 明确不在范围内

- 内核/虚拟化逃逸、推测执行侧信道
- 物理接触、恶意固件
- 模型供应商或宿主操作系统账号被攻陷
- 资源耗尽型 DoS（仅部分：有限额）
- **经审查后放入沙箱的内容的机密性**——这是边界本身的定义
- **被允许来源所返回数据的敏感性**——只做来源控制，不做内容脱敏

## 7. 需要被测试的不变式

1. **准入默认阻断**：命中高危模式的文件无法无声进入，override 必须留痕。
2. **准入完整**：每个进入沙箱的路径都有一条审查记录。
3. **快照干净**：箱内快照不含任何未经声明的凭据。
4. **出站对账**：每个出站请求恰好对应一条审计记录。
5. **可撤销**：宿主删除凭据后，下一次调用立即失败。
