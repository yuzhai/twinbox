# 方案分析：业界做法、差异与目标方案

本文回答三件事：业界有哪些可行做法、它们差在哪、在本文的需求下应该选哪一个。

## 0. 需求基线

需求来自两处：题面（安全优先、桌面级、易用、主流 agent、MCP 零敏感配置）与
`docs/problem.md` 的判据。拆成可打分的条目：

| 编号 | 需求 | 权重 | 性质 |
| --- | --- | --- | --- |
| R1 | 隔离：宿主机文件与网络在箱内不可达 | 10 | 门槛 |
| R2 | 凭据零接触：箱内不存在任何真值 | 20 | **硬门槛** |
| R3 | 工作空间显式声明，进入需审查可追溯 | 10 | 门槛 |
| R4 | 主流 agent 多兼容（≥3 家） | 8 | 门槛 |
| R5 | MCP 配置零敏感信息 | 15 | **硬门槛** |
| R6 | 桌面可安装：无需 root、无常驻守护进程 | 10 | 门槛 |
| R7 | 多轮会话：状态持久、重启无感 | 10 | 门槛 |
| R8 | 鉴权可外置：可对接外部工具（SSH / 云 API） | 4 | 加分 |
| R9 | 环境完整且可复现 | 5 | 门槛 |
| R10 | 主张可验证：每条安全承诺有对应命令 | 8 | 门槛 |

**硬门槛**不满足直接出局，不参与加权。R11（交付成本）作为独立的可行性否决项，不进权重。

## 1. 方案地图

按"问题被谁解决"分七层，每层的候选实现互不替代：

| 层 | 要解决的问题 | 代表实现 |
| --- | --- | --- |
| L1 隔离执行 | 进程能看到什么 | bubblewrap、nsjail、gVisor、Kata、Firecracker、macOS Seatbelt |
| L2 环境供给 | 工具链从哪来 | 宿主根只读挂载、OCI 镜像解包、只读镜像 + FUSE、nix、常驻容器 |
| L3 凭据隔离 | 密钥在哪、以什么形式被使用 | 出站代理注入、Vault/Secretless Broker、短时令牌、受限 ssh-agent |
| L4 工具与授权 | agent 能做什么 | MCP 网关、能力令牌、策略引擎（OPA/Cedar）、审批闸门 |
| L5 会话与状态 | 多轮怎么持续 | 无状态、宿主持久状态、overlay + patch、快照/暂停恢复 |
| L6 鉴权外置 | SSH / 云 API 怎么不落地 | 宿主侧执行器、agent 代理、STS/OIDC 联合 |
| L7 审计与留存 | 出了事怎么查 | 出站审计、会话录制、eBPF、持久状态的清理策略 |

## 2. 逐层差异

### L1 隔离执行

| 方案 | 原理 | 差异点 | 与需求冲突 |
| --- | --- | --- | --- |
| bubblewrap | 非特权命名空间 + bind mount | 无 root、毫秒启动、共享内核 | R1 只能算中高 |
| nsjail | 命名空间 + seccomp | 策略更细，安装略重 | 桌面安装成本 |
| gVisor | 用户态内核 | 隔离强，系统调用兼容性差 | 需 root 安装；工具链与 MCP 生态易踩坑 |
| Kata | 每容器一轻量 VM | 隔离强，需虚拟化与守护进程 | 与 R6 直接冲突 |
| Firecracker | microVM | 隔离最强、启动快 | 需 KVM、文件共享与网络要自建；R11 不满足 |
| 平台原生容器（Apple Containerization / WSL2） | 每容器一轻量 VM 或 OS 集成运行时 | macOS 上隔离强于 Linux 容器，且无需第三方 daemon | 受系统版本与芯片限制；文件共享走 virtiofs `/mnt/c` |
| Seatbelt | macOS 内核沙箱 | 系统自带、零安装 | 能力弱于 VM，需自建策略 |

差异的本质是**隔离强度与部署成本的斜率**：从 bwrap 到 microVM，强度提升有限（因为威胁模型里 agent
不是内核攻击者），而成本陡增。但平台原生容器改变了这个斜率——它把"每容器一 VM"的成本压到了
系统内置的程度，因此在 macOS / Windows 上应当直接采用。

### L2 环境供给

| 方案 | 可复现 | 与既有环境一致 | 首次成本 | 与需求冲突 |
| --- | --- | --- | --- | --- |
| 宿主根只读挂载 | 否（随发行版漂移） | 是（就是本机） | 0 | R9 不满足 |
| OCI 镜像解包 | 是 | 是（同源镜像） | 数十秒，一次性 | 需构建步骤（可接受） |
| 只读镜像 + FUSE | 是 | 是 | 接近 0 | 依赖 FUSE，桌面兼容性待验 |
| nix | 是 | 否 | 高 | 学习成本 |
| 常驻容器（自管 daemon） | 是 | 是 | 低 | 需守护进程，R6 冲突 |
| 平台原生容器（交运行时启动） | 是 | 是 | 低 | 受系统版本限制；跨 VM 文件共享语义弱 |

关键差异：**"完整"不等于"可复现"**。宿主根挂载最省事，但它把发行版版本变成了隐式依赖，
跨天会话会出现无法复现的问题。

另一个差异点在"谁负责挂载"：由我们自己 bind mount（宿主根、解包目录）时，挂载表完全可控；
交给平台容器运行时（macOS / Windows）时，文件共享由 virtiofs `/mnt/c` 承担，
**隔离更强但文件语义更弱**，两者不能同时最优。

### L3 凭据隔离

| 方案 | 箱内有真值 | 对 agent 透明 | 与需求冲突 |
| --- | --- | --- | --- |
| 出站代理注入（占位符） | 否 | 是 | 无 |
| Vault / Secretless Broker | 否 | 否（需改造客户端） | 部署重；R6 冲突 |
| 短时令牌下发 | 是（限域短时） | 是 | 仅适用可再生凭据 |
| 受限 ssh-agent | 否 | 是（`IdentityAgent`） | 仅适用 SSH |
| 密钥管理器注入环境变量 | **是** | 是 | R2 直接违反 |
| 静态配置写 token | **是** | 是 | R2、R5 直接违反 |

差异的本质是**"能用"与"能读"是不是同一件事**。凡把值注入进程的方案，都只是把存储位置换了。

### L4 工具与授权

| 方案 | 凭据位置 | 授权粒度 | 与需求冲突 |
| --- | --- | --- | --- |
| MCP 网关 + stdio 代理 | 宿主侧 | 工具 / 参数级 | 无 |
| 能力令牌（句柄） | 宿主侧 | 句柄级 | 需生态支持 |
| 策略引擎（OPA/Cedar） | 与凭据无关 | 表达力强 | 需要写策略，与"零配置"冲突 |
| 审批闸门 | 与凭据无关 | 动作级 | UX 成本 |

差异：前两者解决"密钥不在箱内"，后两者解决"能做什么"。**两者不是替代关系**，但后者在 36 小时内只值得做一条垂直切面。

### L5 会话与状态

| 方案 | 多轮体验 | 安全 | 与需求冲突 |
| --- | --- | --- | --- |
| 无状态 | 差 | 好 | R7 冲突 |
| 宿主持久状态（per-workspace） | 好 | 中（需留存策略） | 无 |
| overlay + 出箱 patch | 好 | 好 | 实现复杂 |
| 快照 / 暂停恢复 | 好 | 中 | 桌面不可行（依赖 VM 或 CRIU） |

差异：**"持久"与"常驻"是两件事**。状态放磁盘可以既多轮又保持进程可随时重建。

### L6 鉴权外置

| 方案 | 机制 | 适用 | 与需求冲突 |
| --- | --- | --- | --- |
| 宿主侧执行器（代执行） | 请求送宿主，凭据不出宿主 | 云 API、管理操作 | 无 |
| 受限 agent 代理 | 箱内只有签名 socket | SSH、git over SSH | 无 |
| 短时令牌 | 签发限域令牌给箱内 | 对象存储、上传类 | 仅可再生凭据 |
| OIDC / STS 联合 | 用身份换临时凭据 | 云资源 | 需要身份提供方 |

差异：**SSH 与云 API 不是同一类问题**。前者是身份，不可降权，只能代签；后者多数可再生，可以短时下发。

### L7 审计与留存

| 方案 | 成本 | 覆盖 | 与需求冲突 |
| --- | --- | --- | --- |
| 出站审计 + 对账 | 低 | 出站请求 | 无 |
| 会话录制 | 中 | 交互过程 | 存储与隐私 |
| eBPF 运行时监控 | 高 | 系统调用 | 桌面不适用 |
| 持久状态清理策略 | 低 | 磁盘残留 | 无 |

## 3. 平台差异与后端映射

"容器通用且跨平台"这个判断需要修正：macOS 与 Windows 已各自提供系统自带的容器运行时，
"跨平台"不再意味着必须依赖第三方虚拟机。但这也不意味着一个后端能跑遍三平台。

| 平台 | 后端 | 隔离 | 安装成本 | 文件语义 | 脚本兼容 |
| --- | --- | --- | --- | --- | --- |
| Linux | bubblewrap | ◐ 共享内核 | ● 无依赖 | ● 原生 | ● |
| Linux | 容器（rootless / daemon） | ◐ 共享内核 | ◐ 需守护进程 | ● 原生 | ● |
| macOS | 系统容器（每容器一轻量 VM） | ● | ● 系统自带，受版本与芯片限制 | ◐ virtiofs | ◐ 新 CLI，非 Docker 兼容 |
| macOS | 第三方容器（Docker Desktop / Colima） | ◐ 单 VM 内共享内核 | ◐ 需安装第三方 | ◐ virtiofs | ● |
| macOS | Seatbelt | ◐ 共享内核 | ● 系统自带 | ● 原生 | ○ 需自建策略 |
| Windows | WSL2 容器 | ◐ WSL 内共享内核 | ● 系统自带 | ◐ `/mnt/c` 跨边界慢 | ◐ |

三个结论：

1. **没有通用最优解**：Linux 上 bwrap 更轻、文件语义更好；macOS 上系统容器隔离更强且零安装；
   Windows 上 WSL2 容器是唯一现实路径。
2. **跨平台成本集中在外壳两层**：L1（隔离）与 L2（环境供给）随平台变；L3–L6（凭据、工具、会话、
   鉴权）与平台无关，不需要重写。
3. **profile 可跨后端复用**：同一份 OCI 镜像，Linux 上交给 bwrap 挂载，macOS 上交给系统容器运行时。

因此正确形态是：**一套语义 + 每平台用它的原生运行时**，而不是"选一个跑遍三平台"。

| 组合 | 组成 |
| --- | --- |

## 5. 匹配度

矩阵以 **Linux 桌面**为基准；其他平台的差异见 §3，这里只标变化方向，不重复计分。

● 完全满足（1.0）　◐ 部分满足（0.6）　○ 不满足（0）

| 组合 | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 | R9 | R10 | 加权分 | 硬门槛 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **A** | ◐ | ● | ● | ● | ● | ● | ● | ◐ | ● | ● | **94** | 通过 |
| B | ● | ● | ◐ | ● | ◐ | ○ | ◐ | ● | ● | ● | 79 | 通过 |
| E | ○ | ● | ◐ | ○ | ◐ | ● | ● | ◐ | ◐ | ◐ | 68 | 通过 |
| D | ● | ◐ | ◐ | ◐ | ◐ | ○ | ● | ◐ | ● | ◐ | 64 | 通过 |
| C | ● | ◐ | ◐ | ◐ | ◐ | ○ | ◐ | ◐ | ● | ● | 63 | 通过 |
| F | ○ | ○ | ○ | ● | ○ | ● | ● | ○ | ◐ | ○ | 22 | **不通过** |

结论不是"A 每一项都最强"，而是**A 是唯一没有任何一项掉到 ○ 的组合**。C 与 D 在隔离上更强，
但在桌面安装与可复现上失分；E 在工期上最划算，但只覆盖一家 agent，与 R4 冲突。

平台带来的分差（只标方向，不重算总分）：

| 平台 | 组合 A 的变化 | 原因 |
| --- | --- | --- |
| Linux | 基准 | — |
| macOS | R1 由 ◐ 升为 ●；R4 略降 | 系统容器每容器一 VM；新 CLI 与既有脚本兼容性弱 |
| Windows | R1 保持 ◐；R9 略降 | WSL2 共享内核；跨边界文件语义弱 |

组合 B 在 macOS 上的 R6 也应从 ○ 调到 ◐：那里容器是系统自带能力，不再是第三方负担；
但它的配置成本与凭据组件部署问题不变。

## 6. 目标方案

```
宿主（可信）                                     沙箱（不可信）
┌───────────────────────────────────┐          ┌──────────────────────────────┐
│ profile: OCI 镜像解包（只读）     │── ro ───▶│ 完整工具链                    │
│ workspace: 显式声明 + 入箱审查    │── rw ───▶│ /workspace                   │
│ state: homes/<workspace>          │── rw ───▶│ $HOME（缓存 / 历史 / 配置）   │
│ auth: 宿主侧执行器 + agent 代理   │── sock ─▶│ 请求桩 / IdentityAgent        │
│ 出站代理 · MCP 网关 · 审计        │── sock ─▶│ 127.0.0.1 桥                  │
└───────────────────────────────────┘          └──────────────────────────────┘
      进程随终端存活，退出即销毁；凭据从不落盘
```

逐项理由（对应需求）：

> v1 只交付 Linux 后端。macOS / Windows 的后端映射已确定（§3），接口按可插拔设计，
> 但不在本次实现范围内——这不是能力缺失，而是工期取舍。

| 选择 | 满足 | 理由 |
| --- | --- | --- |
| 平台后端（v1：bubblewrap） | R1 R6 | Linux 上非特权、文件语义原生；macOS / Windows 用系统自带容器后端，接口一致 |
| OCI 镜像解包 | R9 | 可复现，且与既有开发环境同源；容器运行时只在构建期出现 |
| 出站代理 + 占位符 | R2 | 箱内无真值，且对 agent 透明 |
| MCP 网关 + stdio 代理 | R5 | 一套实现覆盖多家 agent，配置里只有命令名 |
| 宿主持久状态 | R7 | 多轮靠磁盘，不靠常驻进程 |
| 宿主侧执行器 + agent 代理 | R8 | SSH 与云 API 分别用代签与短时代执行 |
| 出站审计 + 对账 | R10 | 每条承诺都能用命令核对 |

**明确放弃**及理由：

| 放弃 | 理由 |
| --- | --- |
| Vault / Secretless Broker | 部署形态与"桌面可安装"冲突；其租约与审计模型值得借鉴 |
| OPA / Cedar | 要求用户写策略，违反零配置 |
| 把容器运行时作为 Linux 默认后端 | 在 Linux 上会把安装成本转嫁给用户；macOS / Windows 上相反，系统容器是首选 |
| microVM | 36 小时不可交付，且演示机未必具备条件 |
| 快照 / 暂停恢复 | bwrap 无此能力，靠磁盘状态替代 |
| 通用 TLS 中间人 | 增加 CA 信任链，收益被"重写 base URL"覆盖 |

## 7. 三个关键取舍

1. **隔离强度 vs 桌面可安装**：选前者会让 R6 崩，选后者会让 R1 只能算"中高"。
   因为威胁模型里 agent 不是内核攻击者，R1 的中高已足够。
2. **环境可复现 vs 构建成本**：选可复现要多一次构建，但换来跨天会话的稳定性；构建放在工具侧，
   用户仍然零配置。
3. **多轮 vs 进程易变性**：状态放磁盘能同时要，代价是必须承担"留存审查"与清理策略。

## 8. 演进

| 阶段 | 内容 | 触发的需求变化 |
| --- | --- | --- |
| v1 | 本文目标方案的全部组件 | — |
| v2 | 工作负载身份替代静态密钥；破坏性动作审批；macOS 后端 | R2 强化、R8 扩展 |

## 9. 结论

- 业界在**隔离执行**与**LLM 侧密钥管理**上已成熟，在**桌面 agent 的凭据隔离**与**MCP 的凭据模型**上仍是空白。
- 目标方案不是把成熟件拼起来，而是在空白处补两层（凭据边界、MCP 代理），其余尽量复用成熟做法。
- **平台层面没有通用最优解**：Linux 用 bubblewrap，macOS 用系统容器，Windows 用 WSL2 容器；
  统一的是 profile、workspace、state、auth 四层语义，不是运行时本身。
- 判断某个功能该不该做，标准只有一条：**它是否落在 R2 与 R5 这两块空白里**。
